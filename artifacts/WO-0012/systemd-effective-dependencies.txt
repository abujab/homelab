WO-0012 effective systemd dependencies

Server:
Id=k3s.service
Requires=chrony-wait.service sysinit.target system.slice
After includes network-online.target and chrony-wait.service
The generated base unit remains installer-owned.
Ansible drop-in 10-homelab-server-command.conf resets ExecStart and preserves
the effective server flags with --write-kubeconfig-mode 600.
Ansible drop-in 20-homelab-time-gate.conf owns the time dependency.
Effective K3s properties:
- TimeoutStartUSec=3min
- Restart=always
- RestartUSec=5s

Workers pi4mB02, pi4mB03 and pi4mB04:
Id=k3s-agent.service
Requires includes chrony-wait.service
After includes network-online.target and chrony-wait.service
Ansible drop-in 20-homelab-time-gate.conf owns the time dependency.
Effective K3s properties on every worker:
- TimeoutStartUSec=3min
- Restart=always
- RestartUSec=5s

Packaged synchronization gate:
TimeoutStartUSec=3min
RemainAfterExit=yes
ExecStart uses chronyc waitsync

Late recovery:
- homelab-k3s-time-recovery.timer enabled on every node
- OnBootSec=60s
- OnUnitInactiveSec=60s
- each recovery probe uses `chronyc waitsync 1 0.1 0.0 1`
- K3s receives a non-blocking start request and its actual state is polled
- K3s start attempt and effective systemd start job are bounded at 180 seconds
- failure, timeout or restart activity triggers an explicit stop
- success requires ActiveState=active
- failure cleanup requires no start job, transitional state or auto-restart
- recovery TimeoutStartUSec=3min 45s
- any completed synchronized-time attempt leaves the oneshot service active;
  K3s state distinguishes successful start from contained failure
- `systemctl list-timers` then reports no NEXT trigger

Fresh installation:
- INSTALL_K3S_SKIP_START=true creates the server or agent unit without starting it
- Ansible asserts the new unit is inactive
- the Chrony drop-in is installed and systemd is reloaded
- only then is K3s started through the gated unit

Change-driven reconciliation:
- helper/service/timer changes reload systemd, stop/reset recovery and rearm the timer
- diagnostic-only changes do not restart K3s
- unchanged runs do not reload systemd, reset recovery or invoke handlers

`systemd-analyze verify` passed for chrony-wait, the recovery service and timer,
and the applicable K3s unit on every node.
